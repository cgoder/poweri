# Spec: pi 万人 Agent 平台（生产级容器部署）

## Problem Statement

要为一个面向约 1 万名用户的 Agent 平台做生产级部署。平台接收用户的请求（聊天、工具调用、其他 Agent 任务），由网关路由分发到一个个容器化的 Worker Pod 里处理。硬性要求：每个用户的所有数据（文件、聊天记录、执行记录）**不能丢失、不能互相混淆**。

难点在于 pi（pi-coding-agent）本身是一个本地进程：无 HTTP server、无认证、无多租户，RPC 协议走 stdin/stdout。要把 pi 变成可服务上万人、数据强隔离的生产平台，需要一整套容器化 + 网关 + 存储的架构，而不是把 pi 简单塞进一个容器。

## Solution

构建一个多租户 Agent 平台：

- **无状态、水平扩展的网关层**（前挂负载均衡）：承接用户请求，负责认证、路由、业务处理与每用户成本核算。所有状态外置——用户数据在 per-user PVC，user↔session 映射与记账在元数据存储。
- **温池 + 按请求调度 Worker Pod**：每次请求调度一个挂载该用户 PVC 的 Pod（K8s 无法热挂 PVC，故按请求创建）。温池缓冲空闲 Pod、自动伸缩以消除冷启动。Pod 内跑 `pi --mode rpc` 子进程 + 一个 stdio↔WebSocket 桥，把 pi 的 JSONL RPC 暴露成网络端点。
- **数据强隔离**：每用户一块独立 PVC（物理隔离，文件 + 聊天 + 执行记录一体，均基于 pi 的 JSONL 会话）。
- **会话续接**：无状态 Pod 从 PVC 上的会话 JSONL 用 `--session` 续接；新对话用 `--no-session`。
- **并发安全**：同一会话内串行，跨会话并行，避免写坏同一 JSONL。
- **容器级隔离**：非 root、CPU/内存限额、NetworkPolicy 仅放行模型 API 与存储。
- **可观测**：网关聚合每用户 token/成本（来自 pi RPC 事件），结构化 JSONL 日志接管道。
- **User Memory（越来越懂用户）**：每用户跨会话累积的记忆持久化在其 PVC 上（工作区文件），物理隔离、跨会话保留；由 pi 扩展在执行循环内动态读写（机制已定）。
- **计量 + 账单**：聚合每用户资源/数据/模型用量，按定价规则生成账单（不含支付网关）。

## User Stories

1. 作为用户，我想发起一次聊天请求，以便获得 Agent 的回答。
2. 作为用户，我想在我的对话里继续追问，以便接着上次的上下文，而不丢失历史。
3. 作为用户，我想同时开多个独立的对话（多标签页/多任务），以便并行处理不同事项。
4. 作为用户，我想在同一对话里看到流式输出（消息增量、工具执行过程），以便实时了解进展。
5. 作为用户，我想让 Agent 在我专属的工作区里读写代码文件，以便它操作我的项目。
6. 作为用户，我想让 Agent 执行工具命令（bash、git 等），以便完成实际开发任务。
7. 作为用户，我想我的历史聊天记录在任何设备/任何 Pod 上都保持一致，以便随时续接。
8. 作为用户，我想我的文件和历史**不会与其他用户混淆**，以便保证隐私与数据正确。
9. 作为用户，我想我的数据在平台重启、Pod 崩溃后**仍然存在不丢失**，以便信任平台。
10. 作为用户，我想在一段时间后再回来续接某个旧对话，以便找回当时的上下文。
11. 作为管理员，我想给每个用户分配独立的存储卷，以便实现存储层物理隔离。
12. 作为管理员，我想按需伸缩 Worker Pod 数量，以便在高峰与低谷之间平衡成本与吞吐。
13. 作为管理员，我想让任一 Pod 都能接任一用户的请求（无粘性），以便从容应对 Pod 故障。
14. 作为管理员，我想在 Pod 内以非 root 用户运行并设资源限额，以便收窄被注入工具的影响面。
15. 作为管理员，我想限制 Pod 的对外网络（仅模型 API 与存储），以便防止数据外泄。
16. 作为管理员，我想跟踪每个用户的 token 用量与成本，以便计费、配额与容量规划。
17. 作为管理员，我想查看结构化的执行/聊天日志并跨网关+Pod 追踪，以便排障与审计。
18. 作为管理员，我想在会话内对同一用户的请求串行化，以便防止并发写坏会话记录。
19. 作为管理员，我想以不可变 + 锁版本的方式升级 pi 镜像，以便可复现、可回滚。
20. 作为管理员，我想为平台提供健康检查与就绪检查，以便可靠地滚动发布与自愈。
21. 作为网关，我想认证每个请求并把请求路由到能访问该用户数据的 Pod，以便安全地分发工作。
22. 作为网关，我想把 Pod 的流式事件转发给客户端，以便支撑实时交互。
23. 作为网关，我想把同一会话的并发请求串行排队，以便维护会话完整性。
24. 作为网关，我想在会话续接时定位并挂载正确的用户 PVC，以便无状态地恢复上下文。
25. 作为网关，我想在鉴权通过后把用户的会话映射与记账写入元数据存储，以便水平扩展无状态。
26. 作为 Worker Pod，我想通过 stdio↔WebSocket 桥暴露 pi 的 RPC，以便被网关网络驱动。
27. 作为 Worker Pod，我想在启动时挂载请求用户的 PVC 并从其上续接会话，以便作为无状态工作单元运行。
28. 作为 Worker Pod，我想在请求结束后释放（可销毁），以便支撑弹性伸缩与故障替换。
29. 作为用户，我想让平台记住我的偏好与过往（User Memory），以便每次交流都更贴近我的意图、越来越懂我。
30. 作为用户，我想我的记忆与历史在任意会话/设备/Pod 上都能访问，以便跨时间一致地积累。
31. 作为用户，我想我的记忆与其他用户完全隔离、不丢失，以便隐私与数据安全。
32. 作为管理员，我想为每个用户维护独立的记忆存储（随其 PVC 持久化），以便记忆长期累积且隔离。
33. 作为管理员，我想聚合每个用户的资源/数据/模型用量，以便统计与审计。
34. 作为管理员，我想按定价规则由用量生成账单，以便向用户计费。
35. 作为管理员，我想查看用户维度的资源与数据统计报表，以便运营与容量规划。
36. 作为管理员，我想在平台上线时把已有的用户档案/画像/历史使用记录初始化进每个用户的 User Memory，以便老用户上线即被理解。
37. 作为架构师/开发者，我想在本机 macOS + OrbStack（含 K8s 集成）上跑一个最小端到端验证（容器化 pi + 桥 + 网关），以便小步迭代、快速获得反馈、及时修正整体架构。
38. 作为测试组织者，我想为多名测试用户各提供一个可视化界面（基于 pi-web 容器的 Web UI，每用户一实例挂各自 PVC），以便多人在真实环境里可视化地并发操作、观察多租户隔离与续接行为（ticket 15）。

## Implementation Decisions

- **每用户独立 PVC**（ADR-0001）：用户数据物理隔离于存储层，含工作区文件与 pi 会话历史。备份/快照/删号按用户切分。
- **stdio↔WebSocket 桥**（ADR-0002）：每个 Pod 内 `pi --mode rpc` 子进程 + 轻量 shim，把 pi 的 JSONL 帧协议暴露为 WebSocket。网关写入命令（`prompt`/`steer`/…）并读取事件流（`message_update`/`tool_execution_*`/…）。保持进程隔离、语言无关。
- **无状态水平扩展网关层**（ADR-0003）：状态外置（per-user PVC + 元数据存储），网关按需水平伸缩，无单点故障。
- **温池 + 按请求调度 Pod**（ADR-0004）：请求发生时调度一个挂载该用户 PVC 的 Pod；温池缓冲 + 自动伸缩抵消调度延迟。K8s 卷在 Pod 创建时固定，故不可跨用户热复用。
- **会话内串行、跨会话并行**（ADR-0005）：同一会话一个 in-flight 请求，其余排队；不同会话并行（各自 JSONL 文件）。
- **每用户成本核算 + 结构化日志**（ADR-0006）：网关从 RPC 事件聚合 token/成本入元数据存储；JSONL 事件直通日志管道；跨网关+Pod 追踪。
- **会话续接**：新对话 `--no-session`；追问 `--session <路径>` 从 PVC 的 JSONL 恢复。
- **pi 以 `--mode rpc` 子进程运行**，headless；每次请求按需启动/复用长驻子进程（短处理一次性、长对话复用）。
- **元数据存储**：记录 user→session 映射、每用户配额/记账、会话状态，支撑网关无状态路由。
- **容器级隔离**：非 root 用户、CPU/内存/磁盘限额、NetworkPolicy 仅放行模型 API 与存储、仅挂载该用户 PVC。微 VM 隔离留作后续选项。
- **流式转发**：客户端 SSE/WS ↔ 网关 ↔ Pod WS，网关轻量逐跳转发（当前规模足够；pub/sub 留作扩展）。
- **认证**：网关统一鉴权（OAuth/企业 SSO），Pod 不直接暴露给客户端。
- **健康/就绪**：桥暴露存活探针，pi 侧以 `get_state` RPC 校验成功；就绪校验模型可用（`ModelRuntime.getAvailable`）。
- **更新**：不可变 + 锁版本镜像（`@…/pi-coding-agent@<版本>`），滚动替换；容器内 `PI_OFFLINE=1` 关闭自更新与 pi.dev 外呼。
- **配置/凭据注入**：模型凭据经 secret 管理注入环境变量；自定义 provider/model 走 `models.json`（`apiKey` 支持 `$ENV_VAR` 插值），全局设置走 `settings.json`。
- **桥协议细节来自调研**：pi RPC 为严格 LF 分隔 JSONL（`docs/rpc.md`），headless 下扩展 UI 经 `extension_ui_request/response` 子协议，TUI 专属方法为 no-op。
- **User Memory（跨会话用户画像，ADR-0008）**：持久化在每用户 PVC 上的工作区文件，物理隔离、跨会话累积。**机制已定：pi 扩展**——扩展在工作区维护 memory 文件，随 agent 执行循环动态读写/注入，以贴合“提高执行能力与执行过程”的目标；扩展代码打包进每个 Pod 镜像。**设计定稿（docs/design/08-user-memory.md）**：三节记忆（画像/事实/偏好）存 `/workspace/.poweri/memory/`；`before_agent_start` 修改 `event.systemPrompt` 按 `POWERI_MEMORY_BUDGET`（默认 3000 tokens）上限截断注入（生态标准路径，T18 自 `before_provider_request` 迁入）；agent 回合内调用 `remember` 工具增量写入（零额外模型调用）；`scripts/init-memory.mjs` 上线时幂等初始化存量数据。**生态选型定案（ticket 14，实证 `docs/research/pi-memory-deep-research.md`）**：不替换为 pi-memory/hermes——三包注入路径（`before_agent_start` systemPrompt）实证可用，但 pi-memory 会话级 exit summary（每含工具请求 +1 次 LLM，无开关）与 daily 无锁写与平台“每请求一进程 + 跨会话并行”冲突；保留自研 + 移植最佳实践（ticket 18：注入点迁移 before_agent_start / 稳定快照 / 删除恢复 / daily 日志加锁评估）。
- **存量数据初始化（Legacy user data onboarding）**：平台上线前已有的用户档案/画像/历史使用记录需并入 User Memory。方案：**上线时按用户一次性初始化**到其记忆体系（写入各用户 PVC 的 memory 文件），分批、可重试、幂等；用户首次运行时加载作为兜底。
- **用量计量 + 账单生成（ADR-0007）**：计量源 = pi RPC 事件的 token/成本 + 平台侧资源/数据指标（CPU/存储/带宽/出站）；聚合入元数据/计量存储；按定价规则生成每用户账单。支付网关不在范围。

## Testing Decisions

- **本地验证环境（小步迭代）**：测试与验证跑在本机 macOS 上，Docker 用 OrbStack（含 K8s 集成）。以最小端到端 PoC 为验证循环——容器化 pi + stdio↔WS 桥 + 网关——逐步验证每一层、快速反馈并修正架构，而非一次搭完再测。
- **多用户可视化验证（ticket 15）**：pi-web 容器每用户一实例（挂各用户 PVC），多人各自操作界面观察真实 pi 并发/隔离；pi-web 直接驱动 pi（进程内 SDK），网关层行为仍由 fake 主缝 + verify 脚本覆盖。
- **主测试缝：网关客户端 API**。以 fake 内存 Pod 替换真实 pod 层，把客户端请求灌进网关，端到端验证：认证、路由、会话内串行、会话续接、每用户成本核算、流式转发。只测外部行为，不测实现细节。
- **第二薄缝（可选）：stdio↔WebSocket 桥**。用真实或脚本化 `pi --mode rpc` 单独验证帧格式、命令/事件映射、子进程生命周期。
- **模块**：网关路由与并发控制、会话续接与 PVC 挂载决策、成本核算聚合、流式中继；桥的帧解析与命令映射；计量聚合与账单生成。
- **计量与账单**：验证 RPC 事件与平台指标正确聚合到 per-user 计量、定价规则正确产出账单。
- **memory 注入**：机制定后，验证记忆在每次请求被注入且不跨用户泄漏。
- **先例**：本项目为绿地（greenfield），无既有测试先例——以网关 API 端到端测试建立模式。
- **好的测试**：以"一个用户请求 → 正确的会话被续接/新建 → 事件正确流回 → 用量被记账"为断言，而非 pi 内部细节。

## Out of Scope

- **支付网关 / 收款**（Stripe 等实收）不在范围——本 spec 只做到账单生成。
- pi 本体（上游工具）的任何修改。
- 客户端 UI / 前端（本 spec 只覆盖后端平台）。
- 微 VM / Kata / gVisor 级执行隔离（当前容器级足够，留作后续）。
- 发布/订阅式流式解耦（Redis/Kafka）（网关同步转发足够，留作扩展）。
- 多地域 / 跨集群高可用（未在本 spec 范围）。
- pi 的扩展 / 包 / 主题编写（用户内容，非平台能力）。

## Further Notes

- 下一步用 `/to-tickets` 把本 spec 拆成可执行 ticket。
- 待定细节：同一用户跨会话并行时，若两个会话触碰同一工作区文件，可能产生文件级竞争（用户侧行为，非数据损坏）；可在实现时决定是否加更细粒度锁。
- 桥是每个 Pod 内唯一的自有代码，应保持最小并独立可测。
- 会话存储目录若与工作区分离，可用 `PI_CODING_AGENT_SESSION_DIR` 指向独立可写卷。
- **User Memory 实现选型待定（决策挂起）**：ticket 08 已按自研 pi 扩展实现并验证（`1ed52d7`，机制：remember 工具零额外 LLM 写入 + `before_provider_request` 预算截断注入）。调研发现 pi 生态存在更成熟包（pi-memory 0.4.0 与自研同构且多出 KV 缓存稳定快照/daily 日志/删除恢复；hermes 0.9.2 功能最全但有原生依赖与后台 LLM 成本；observational 3.0.3 解决长会话压缩、形态错配）。**结论：不在此处定案**，见 `docs/research/pi-memory-extensions.md`，后续单独 deep research（ticket 14）后再决定是否以包替换/移植。
