# Mature open-source first, never hand-roll what exists

Any capability that a mature open-source project or package already solves must use that project/package instead of in-house code — provided the architecture accepts it. This is a platform-wide rule for every entry point: gateway, worker images, bridge, web shell, and verification scripts.

**Mechanism (decided):** before writing any non-trivial utility that exists in the ecosystem, (1) research the candidate project/package rigorously — industry best practice, maintenance status, license, compatibility with the locked runtime (pi 0.83.0, Node 24) and with this repo's architecture (per-user PVC, gateway routing, stateless workers); (2) only adopt it if it is best practice AND fits; (3) otherwise — and only then — write the minimum in-house code, with a `ponytail:` comment naming the gap. Verification scripts follow the same rule: e.g. SSE parsing in `scripts/verify-24.mjs` and the pi-web (agegr) fork client use `eventsource-parser` (rexxars, zero-dependency, the same parser Vercel AI SDK uses) rather than hand-rolled chunk slicing. Frozen verification scripts of closed tickets are historical artifacts and are not retrofitted.

**Ecosystem package decision (2026-08-02, ticket 24):** replaced hand-rolled SSE frame parsing with `eventsource-parser` v3.1.0 in `lib/gateway-client.ts` (parseSseFrame adapter + incremental `createParser` feed) and `scripts/verify-24.mjs`. Researched before adopting: confirmed the canonical package is `eventsource-parser` by rexxars (no rename; `@eventsource/parser` is not official), zero dependencies, used internally by Vercel AI SDK (pinned >=3.0.8) and the OpenAI SDK — the de-facto industry standard for SSE parsing in JS across Node/browser/Deno, with `createParser` and `eventsource-parser/stream` (TransformStream) entry points. Fits the architecture: source-agnostic incremental parser, no runtime lock-in, works in the fork's Node 24 + TypeScript type-stripping setup. Out of scope and still hand-rolled: SSE *writing* (gateway `server.mjs`) — that is a streaming-response concern on the server side, not a parse concern this rule covers.
